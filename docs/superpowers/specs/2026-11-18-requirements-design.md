# 需求模块设计：先设计流程，实现后对照

日期：2026-11-18。状态：等主人确认。

## 1. 意图

接到业务需求时，先把"改完之后的流程"设计出来、让人确认，再写代码；写完后把代码分析出的流程和设计的流程对照，
差在哪里一眼能看到。需求和它的设计流程存在**使用 pystepmap 的那个项目里**，跟着代码走；pystepmap 分析项目时
把它们找出来。

主人的原话：
- "接到需求的时候最好能先设计出来流程图，然后根据流程图来实现，实现后，可以对比实现的流程图和设计的流程图"
- "我想要单独加一个模块来存储业务需求……实现类似 OpenSpec 的功能，但是不要抄袭 OpenSpec"
- "存在使用这个 mcp 的项目中。分析项目代码的时候找到就行了。"
- 不用 superpowers、OpenSpec 也要能单独使用。

## 2. 目标、非目标、反目标

目标
- 一条需求 = 业务说明 + 一份设计的流程（步骤、判断、结局和走向）+ 状态。
- AI 通过 MCP 新建、读取、修改需求；人在平台的画布上看设计的流程图。
- 实现后自动对照：设计里有、代码里没有的；代码里有、设计里没有的；走向不一致的。
- 设计里的每个结局有没有测试走到（用已有的"没走到的结局"）。
- 需求文件是纯文本，能在代码评审里读、能手改。

非目标（这一版不做）
- 在画布上用鼠标拖节点来画设计图（设计由 AI 或人写成文本，平台只负责画出来）。
- 任务拆分、排期、指派。
- 需求之间的依赖关系。
- 多人同时编辑的冲突处理（交给 git）。

反目标
- 变成另一套要人读的长文档：需求的主体必须是流程，说明文字是辅助。
- 对照结果说错：只报能从图上确定的差异，配不上的如实说"配不上"，不猜。
- 悄悄改项目文件：只有明确调用"保存需求"的工具时才写，且只写需求目录。

## 3. 和 OpenSpec 的区别（不照搬）

OpenSpec 的单位是文字规格和它的增量（提案、任务、带场景的需求条目、归档），靠人读文字判断实现对不对。
这里的单位是**流程**：需求的主体是一张设计的流程图，验收是"实现的图和设计的图对得上"加"每个结局有测试走到"，
两项都由工具算出来。不采用它的目录结构、文件名、提案 / 任务 / 归档的做法和措辞。

## 4. 存在哪里、长什么样

项目根目录下 `.pystepmap/requirements/`，一条需求一个 Markdown 文件，文件名 `<编号>-<短标题>.md`，编号 `R001` 起
按已有的最大编号加一。分析时这个目录不当作源码（不是 `.py`），只由需求模块读。

```markdown
# 大额转账要人工复核

- 编号：R003
- 状态：已确认
- 功能线：账户转账

## 说明

单笔超过 5 万的转账不能直接执行，先交人工复核；复核通过再转。

## 设计的流程

​```flow
步骤：查询请求状态
判断：重复提交的请求？
  是：
    结局（跳过）：重复请求，不再处理
步骤：参数校验
判断：需要人工复核？
  是：
    步骤：提交人工复核
    结局（跳过）：已提交人工复核
步骤：执行转账
结局（成功）：转账完成
​```
```

流程的写法（一种很小的缩进文本，行首关键字，冒号全角半角都认）：
- `步骤：标题`、`判断：标题`（下面用 `是：` / `否：` 各带一段缩进的内容）、`循环：标题`（下面缩进的是循环体）、
  `结局（成功 | 跳过 | 失败）：标题`。
- 一段内容从上到下依次执行；`判断` 的分支里没有结局的，走完回到判断后面的那一行。
- 不写的东西：变量、参数、代码。标题就是图上节点的标题。

状态：`草稿` → `已确认`（人确认过设计）→ `已实现`（对照没有差异）→ `已完成`（并且每个设计的结局都有测试走到）。
前两个由人 / AI 写；后两个由对照结果决定，工具只报告"现在够得上哪个状态"，写回文件要明确调用。

## 5. 怎么对照（这一版的规则）

把设计的流程和功能线根函数的图（钻入被调用的、带标记的函数时沿调用展开）都看成"到每个结局的路径上依次经过的
带标题的节点"。

1. 节点按**类型 + 标题**配对（标题先做同样的清理：去空白、去句末标点）。
2. 报告四类差异：
   - 设计里有、实现里没有的步骤 / 判断 / 结局；
   - 实现里有、设计里没有的（只报带中文标题的、在这条功能线上的节点；"未捕获异常退出"这类隐含结局不报）；
   - 结局的分类不一样（设计是失败，实现是跳过）；
   - 走向不一致：设计里到某个结局的路径上依次经过的节点，在实现里到同一个结局的任何一条路径上都不是按这个顺序
     出现的。
3. 功能线找不到（还没实现、或者名字对不上）时说"功能线还不存在"，设计里的节点全部算"没有实现"。
4. 设计解析不了时报第几行、为什么，不做对照。

已知的局限写进文档：靠标题配对，标题改了就配不上（会报成一删一增）；循环体里的走向只比有没有，不比次数。

## 6. 各部分

- **core**（只用标准库）`pystepmap/requirements.py`：读写需求文件、解析流程文本、对照。命令行
  `pystepmap requirements <项目>`：列出需求和各自的对照结果（给不用 Claude Code 的人）。
- **分析**：`analyze` 的图里加 `requirements`（每条需求的编号、标题、状态、功能线、设计的流程、对照结果、
  解析错误）。没有需求目录时没有这个字段，现有项目的图不变。
- **平台**：项目里多一个"需求"列表；点开一条：说明、设计的流程图（用现有画布画）、对照结果（差异标在图上，
  颜色沿用流程差异的绿 / 琥珀 / 删除线）、每个设计结局有没有测试走到。只读，不在界面上改需求。
- **MCP**：`list_requirements`、`get_requirement`、`save_requirement`（新建或整条改写，写项目里的文件；这是 MCP
  里唯一写项目文件的工具，说明里写清楚）、`check_requirement`（重新对照，返回差异和够得上的状态）。
- **skill**：`requirements.md` 的四步换成用这些工具——先 `save_requirement` 写出设计（状态草稿），让用户确认后改成
  已确认，实现，`analyze_project` 后 `check_requirement`，把差异告诉用户。

## 7. 建造顺序

1. core：文件格式、流程文本的解析、对照、命令行。验收：转账示例上写一条需求，对照零差异；故意删一个分支，
   报出少了哪个结局。
2. 分析和平台后端：图里带需求，接口返回。
3. MCP 四个工具和 skill。验收：在一个临时项目里用 MCP 新建需求、实现、对照。
4. 界面：需求列表、设计图、差异。验收：主人看过。

## 8. 我替主人做的决定（可以改）

- 需求文件用 Markdown，流程用缩进文本，不用 YAML / JSON（标准库没有 YAML；JSON 人不好读写）。
- 目录叫 `.pystepmap/requirements/`。
- 状态用中文四个词。
- 界面只读；改需求通过 MCP 或直接改文件。
- 对照按标题配对。

## 9. 实现时改的地方（2026-11-18）

- 流程文本多一种写法：`步骤` 下面可以缩进一个 `失败时：`，写这一步出错被接住之后的内容（转账示例里"执行转账"失败后
  解冻资金就是这样）。
- 需求**不写进图 JSON**：平台和 MCP 每次要用时现读项目里的需求文件，和最新一次分析的图对照。这样改了需求不用
  重新分析就能看到，已有项目的图也不变。（第 6 节"分析"那一条作废。）
- 走向只在功能线的根函数里比；派发出去的任务里的节点只比有没有。
- 循环节点在实现里的标题来自代码（循环上方的注释，没有注释时是 `for … in …` 原文），设计里要写循环就得和它一致；
  不想管循环时，设计里只写循环体里的步骤也对得上。

## 10. 配合 OpenSpec：直接读它的文件（2026-11-18）

主人的原话："我觉的可以搭配 OpenSpec 一起使用，把文档改成直接读 OpenSpec 也是可以的。"

- 项目用 OpenSpec 时，需求、变更、任务由 OpenSpec 管，pystepmap 只做它做不了的那一件事：把设计的流程和代码的流程对照。
  设计的流程写在 OpenSpec 变更的 `design.md` 里的 ```` ```flow ```` 代码块（块里第一行 `功能线：…`），`load_requirements` 把
  `openspec/changes/<变更>/`（不含 `archive/`）和 `openspec/specs/` 下的这种代码块也读成需求。编号是变更名，状态不存。
- `.pystepmap/requirements/` 照旧可用（不用 OpenSpec 的项目）。`save_requirement` 只写这个目录，不写 OpenSpec 的文件。
- MCP 给 AI 的说明按当前目录所在的项目分两种：有 `openspec/` 的说"需求走 OpenSpec，流程写进 design.md"，没有的才说
  "先 `save_requirement`"。原来不分项目一律说后者，在用 OpenSpec 的项目里和它的入口抢。
- 设计的节点一个都没配上时，对照结果多一句说明：多半是标题对不上（代码没打标记），不是没实现。
