# 图 JSON 字段说明

`pystepmap analyze` 输出的图（`-o graph.json`），给画布、MCP 服务等读图的程序用。字段与
`core/src/pystepmap/model.py` 里的 dataclass 一一对应，JSON 里的顺序同声明顺序；读写见 `to_json` / `from_json`。

- `schema_version` 是 1。之后的版本只加字段、不改已有字段的含义；读图时忽略不认识的字段（`from_json` 就这么做）。
  早于稳定标识的旧图没有 `sid` / `sids`，`from_json` 读出来是空串 / 空表；早于分支字段的旧图连线没有 `branch`，
  读出来是空串（怎样认分支见"读连线"第 1 点的回退）；早于完整形式的旧图没有 `title_full`、`subtitle_full`、
  `label_full`，读出来是空串（见"截断与完整形式"）。
- 所有路径都相对 `root`，用 `/` 分隔。行号从 1 起。

## 先说画法

- 一个函数一张图。只有"有意义"的语句出节点：含有意义调用（见"调用"）的语句是步骤；`if` / `elif` / `match` 是判断，
  `for` / `while` 是循环，有处理体的 `except` 是捕获，`return` / `raise` 是结局。没有有意义调用的语句（赋值、日志、
  计数……）不出节点。
- `with`、`try`、`else`、`finally` 自己不出节点：`with` 的上下文表达式里有有意义的调用时出一个步骤，里面的语句接在
  主线上；`try` / `else` / `finally` 体里的语句照常出节点。
- **折叠**：一个分支、循环体或处理体里一个节点都没有（也没有 `return` / `raise` / `break` / `continue`）时，这一块
  不画。`if` 的两个分支（`match` 的所有分支）都折叠掉时不出判断节点，条件（主语、守卫）里有意义的调用合成一个步骤；
  循环头没有有意义的调用、循环体里只有 `break` / `continue`（也没有 `else` 体）时整个循环不画；处理体折叠掉的 `except` 不出捕获节点，
  被它吞掉的异常照常往下走。
- `n1` 总是开始节点，"未捕获异常退出"总是最后一个节点。

## 两种标识：key 与 sid

| | key（一次分析之内的身份） | sid（跨两次分析的稳定标识） |
|---|---|---|
| 函数 | `key`：`相对路径::限定名@定义行`，如 `app/a.py::Svc.run@12` | `sid`：`相对路径::限定名`，如 `app/a.py::Svc.run` |
| 节点 | `id`：`n1`、`n2`……按生成顺序编号 | `sid`：`<节点类型>:<语句头部记号流的 sha1 前 8 位>`，如 `step:3f2a91c0` |
| 功能线 | `id`：根任务函数的 key | `sid`：`line:` 加根任务函数的 sid |

- **key 用来引用。** 图里所有的相互引用（`target`、`passthrough`、`parent`、`call_targets`、`LineTask.function`、
  `common_tasks`、`selfcheck`）都用函数 key 和节点 id。记录插件写的执行记录只带函数 key 和行号，不带节点 id；
  `pystepmap verify` 按行号把记录对应到节点。key 带行号，函数上方多一行就变；节点 id 是位置编号，前面多一个节点，
  后面的都变。
- **sid 用来在两次分析之间找回同一个东西**，例如重新分析后找回平台上手写的标题和分组、比较两次分析的流程差异。
  sid 只用来配对，引用关系照旧用 key。
  - **要配对的两次分析必须用同一个分析目录。** 函数 sid 里的路径相对分析的目录（`root`），功能线 sid 由它而来：
    分析 `backend` 时是 `app/x.py::f`，分析 `backend/app` 时是 `x.py::f`，两者配不上。
  - 不改变节点 sid 的修改：换行重排（格式化工具把调用拆成一行一个参数时通常会顺手加末尾逗号，那就变了，见下）、改缩进、改注释（包括上方的注释，即使标题跟着变了）、函数里别处的修改（只要
    没让这个节点换类型）、文件里别处的修改、把函数挪到文件里别的位置（同文本语句的编号除外，见下）。
  - 改变函数 sid 的：函数改名、移到别的文件、外层的类或函数改名、把 `def` 挪进或挪出类 / 函数（限定名变了）；在它
    前面增删同一限定名的定义（`@overload` 桩、property 的 getter / setter、`try` / `except` 两处定义）会让后面那些
    的 `#n` 移动。
  - 改变节点 sid 的：语句头部的记号变了，包括改引号风格（`'x'` ↔ `"x"`）、加减末尾逗号、给条件加减括号；节点类型变了（判断 ↔
    步骤，例如 `if` 的分支都折叠掉了）。这也可能由别处（同一文件或别的文件）的修改引起：被调用函数的解析结果变了，分支里的调用不再
    算有意义，节点就会出现、消失或换类型。
  - **格式化工具的第一次运行可能一次改变很多节点 sid。** 记号层面的这几种外观修改仍然改变 sid：引号风格、末尾逗号、
    加减括号（给条件、长表达式、`with` 的多个上下文加括号）。所以第一次对一个代码库跑格式化工具（black、ruff format
    之类）时，统一引号、补末尾逗号、加括号会让大批节点的 sid 同时改变，按 sid 保存的数据会大批配不上；之后再跑同一个
    工具、同样的设置，不再改变。
- **唯一性**：函数 sid 在整个图里唯一，节点 sid 在所属函数内唯一（跨函数时用"函数 sid + 节点 sid"），功能线 sid
  在整个图里唯一。重名时按顺序从第二个起加 `#2`、`#3`：同一文件里同一限定名的多处定义（`if` 两个分支各定义一次、
  重复定义）按定义行；同一函数里类型和头部记号流都相同的节点按源码位置；同一根函数的多条功能线按列表顺序（目前每个
  根函数至多一条线）。所以删掉第一处，原来的 `#2` 会变成不带后缀的。
- **配对时 `#n` 只是区分重名的手段，不是身份的一部分**：在前面增删一条同文本的语句，后面那些的编号就移动、指向
  别的语句。所以比较两次分析的流程差异时，不要拿带 `#n` 的 sid 直接相等来配对，也不要只在"同一基础 sid 的一组"里
  按顺序配对（那和 `#n` 相等是一回事）。要把**整个函数**的节点按源码顺序排成一个序列，每个节点取去掉 `#n` 的基础
  sid，对两次分析的两个序列做序列对齐（最长公共子序列，如 Python 的 `difflib.SequenceMatcher`）：重名节点前后那些
  不重名的节点会把它们定住。按节点 sid 保存数据（手写标题等）时，把同一基础 sid 的 `#n` 兄弟当作一组处理。
- **连线没有标识。** 连线只有 `src`、`dst`（节点 id）、`kind`、`label`（判断节点的分支出边还有 `branch`），没有
  `sid`。比较两次分析的连线时，按（起点节点的 sid，终点节点的 sid，`kind`，`label`）配对，起点、终点节点按上一条的
  方法配对（带 `#n` 的节点用序列对齐得到的对应节点，不直接比带 `#n` 的 sid）。同一个函数里这四项相同的连线只有一条。
  `branch` 由起点和 `kind`、`label` 决定，不用参与配对。
- **节点 sid 的"语句头部"**：步骤是整条语句（`with` 取到最后一个上下文表达式为止，每一项的 `as` 目标都不算：
  `with a() as x, b() as y`、`with a() as w, b() as z`、`with a(), b()` 的 sid 相同；两个分支都折叠掉的 `if` /
  `match` 取到条件 / 主语为止）；判断、循环取 `if` / `elif` / `match` / `for` / `while` 到条件（主语、迭代对象）为止；
  捕获取 `except` 到异常类型为止；结局取整条 `return` / `raise`。头部源码按 Python 的分词规则（`tokenize`）分成
  记号，去掉注释、换行和缩进记号，其余记号之间用一个空格连接，再算 sha1：`notify(order)` 和分三行写的
  `notify(\n    order\n)` 都是 `notify ( order )`。标题、文档注释不参与。隐含节点用固定名字：开始 `start`、
  执行到函数末尾 `end:implicit`、未捕获异常退出 `end:uncaught`。
- **实现**：上面的配对和流程差异实现在 `pystepmap.diff`（`core/src/pystepmap/diff.py`，模块说明写了完整规则）。和上面的
  写法相比多了两点：
  - 序列对齐对不上的一段里再配一次：类型相同、文字（标题 + 副标题）相似度不低于 0.6 的，按保持顺序的最多对配上，算
    "改动"，其余才算删除 / 新增（一段太大时不逐对比，全算删除和新增）。
  - 报出的连线变化：只比两端都配上对的连线；节点的增删已经说明了的不单列（在两个留下的节点之间插进 / 删掉节点不报
    连线变化）；但新增的判断 / 循环 / 捕获节点的出边、新增节点的异常连线、留下的判断进新增节点的分支照样报成新增连线，
    看得到新分支通向哪里。删除的节点另给它在旧图控制流上前面最近的留下的节点和那条出边（`after`、`after_label`）。

## 截断与完整形式

标题这类文字是**显示形式**：函数、节点、功能线的 `title`，节点的 `subtitle`，`case` 连线的 `label`。它们都是单行、
空白合并成一个空格；`title` 和步骤的 `subtitle` 最长 60 字，判断 / 循环 / 捕获的 `subtitle`（源码原文）和 `case` 的
`label`（模式原文）最长 80 字，超出时截成前 59 / 79 字加"…"。

被截断时，同名加 `_full` 的字段带**完整的文字**：`title_full`、`subtitle_full`、`label_full`。清理方式和显示形式一样
（单行、空白合并；标题还去掉反引号和 `**`，`case` 模式不去），只是不按 60 / 80 截断；为防异常长的文档注释、源码把图
撑大，最长 2000 字，超出同样截断加"…"。没被截断时没有这个字段（`from_json` 读出来是空串），所以完整文字总是
"`x_full` 不为空就用它，否则用 `x`"。

取自函数文档注释的标题（函数自己的标题、开始节点、调用它的步骤、派发它的步骤、功能线的标题）只用注释第一行的
**第一句**：到第一个句号（。）、分号（；;）、破折号（——）或后面跟着空白的英文句号为止，括号里面的不算，断出来不到
4 个字的不算。第一行不止一句时，整行在 `title_full` 里（只差句末标点时没有）。

- 只加不改：显示形式的值和以前完全一样；去掉所有 `*_full` 字段，图和加这几个字段之前的引擎生成的逐字节相同。
- `branch` 照旧是截断后的 `label`：认分支、配对都按它，不看 `label_full`。连线去重、跨两次分析配对时 `label_full`
  不参与（两个模式截断后相同、连到同一处时仍然只有一条连线，带第一个的完整模式）。
- 开始节点的标题就是函数标题，`title_full` 也相同；功能线的标题取自被截断的函数标题时，`title_full` 是函数的
  `title_full`（标题是"方法 路径"时没有）。

## 顶层（ProjectGraph）

| 字段 | 说明 |
|---|---|
| `schema_version` | 1 |
| `root` | 分析的目录，**绝对路径**。图文件因此和生成它的那份检出绑在一起：换机器、换检出目录要重新分析 |
| `functions` | 函数 key → 函数图，按 key 排序。项目里每个函数（含方法、内部函数）各一张；构建失败的不在，记在 `skipped_files` |
| `lines` | 功能线，按（分组，标题）排序 |
| `common_tasks` | 公共任务的 key：被不少于 `common_task_threshold`（默认 6）个入口派发的任务，不并入各条功能线，自己单独成线 |
| `selfcheck` | 自检结果，见下 |
| `file_hashes` | 相对路径 → 文件内容的 sha256（读到的每个 `.py`，含解析失败的）。和当前文件比对即知图是否过期 |
| `sids` | 函数 sid → 函数 key，按 sid 排序 |

## 函数图（FunctionGraph）

| 字段 | 说明 |
|---|---|
| `key` | 见上 |
| `file`、`qualname` | 相对路径；限定名，同 Python 的 `__qualname__`（`Svc.run`、`outer.<locals>.inner`） |
| `line`、`end_line` | `def` 所在行（不含装饰器）；函数最后一行 |
| `kind` | `route` 接口、`task` 后台任务、`workflow` 工作流、`step` 步骤、`condition` 条件（来自框架装饰器或 pystepkit 标记），其余 `function` |
| `title` | pystepkit 标记里的 `title` → 文档注释第一行 → 函数名，显示形式，最长 60 字 |
| `is_async` | `async def` |
| `sid` | 见上 |
| `marked` | 用了 pystepkit 标记 |
| `group`、`route` | 标记里的分组；接口的 "方法 路径"，如 `POST /pubsub`。同一个函数既有路由装饰器又是工作流（`@workflow`、`@DBOS.workflow()`）或任务时，`kind` 是工作流 / 任务，`route` 照样记下（两个装饰器谁写在上面都一样） |
| `retries` | 任务声明了失败重试 |
| `parent` | 定义在函数里的函数（及函数里定义的类的方法）：外层函数的 key |
| `nodes`、`edges` | 节点和连线，见下 |
| `call_targets` | 本函数里每个解析到（`exact` / `guessed`）的项目内调用的 key（派发不算），按源码顺序去重。包括没画进节点的（折叠掉的分支、构造对象调用的 `__init__`、lambda 体、嵌套定义的装饰器和默认值） |
| `unresolved` | 本函数里每个无法判断目标的调用 `{line, name}`（不论是否进了节点；lambda 体里的不算），按（行，名字）去重 |
| `rule`、`name`、`version` | 只在有值时出现：识别出入口 / 标记的规则集名（`fastapi`、`flask`、`taskiq`、`celery`、`dbos`、`pystepkit`……）；类型是 `function` 的入口上是认出它的方式：`main`（`__main__` 块里调用）、`command`（命令行子命令）、`handler`（挂着项目外对象的装饰器）、`comment`（`# pystepmap: 入口` 注释）、`fallback`（兜底：没有人调用的顶层函数）；pystepkit 工作流的 `name=`、`version=` |
| `title_full` | 只在 `title` 被截断时出现：完整的标题（见"截断与完整形式"） |

## 节点（Node）

| 字段 | 说明 |
|---|---|
| `id` | 见上 |
| `type` | `start` 开始；`step` 步骤：一条语句里有意义的调用；`cond` 判断：`if` / `elif` / `match`；`loop` 循环：`for` / `async for` / `while`；`catch` 捕获：有处理体的 `except`；`end` 结局：`return`、`raise`、执行到函数末尾、未捕获异常退出 |
| `title` | 显示的标题，最长 60 字（见"截断与完整形式"）：被调用函数的标记标题或文档注释、语句上方的注释、源码，依次回退；结局是"返回 …"、"抛出 …"、`outcome(title=…)` 等；`raise HTTPException(...)`（FastAPI / Starlette 的，按 import 认）写成"状态码 说明"，如 `404 用户不存在`（状态码认整数和 `status.HTTP_404_NOT_FOUND` 这样的常量，看不出来时照旧"抛出 …"；没给说明时写状态码的标准说法，如 `401 Unauthorized`） |
| `sid` | 见上 |
| `subtitle` | 步骤：调用的显示名，用 ` + ` 连接，最长 60 字；判断、循环、捕获：条件 / `match 主语` / 循环头 / 异常类型的原文（裸 `except` 为"任意异常"），最长 80 字；其余为空 |
| `line`、`end_line` | 节点代表的语句头部所在的行（范围同 sid 的"语句头部"）。开始节点是 `def` 所在行；执行到函数末尾、未捕获异常退出为 0 |
| `calls` | 头部里有意义的调用，按源码位置（见下"调用"；`match` 另含守卫里的，见"读连线"第 6 点） |
| `end_kind` | 只有结局有：`ok` 正常、`skipped` 跳过、`failed` 失败（`raise` 都是）、`exception` 未捕获异常退出 |
| `fields` | 结局返回的字段（配置 `outcome_fields` 里的名字），值是常量或源码原文 |
| `passthrough` | 转交返回（`return f(...)`，或返回这样一个调用的结果）：`f` 的 key |
| `title_full`、`subtitle_full` | 只在 `title` / `subtitle` 被截断时出现：完整的文字（见"截断与完整形式"） |
| `quiet` | 只在有值时出现：`if` 的分支里没有节点（没有有意义的调用）、但改了变量时，这条分支做了什么——`{"yes" 或 "no": 分支里的赋值语句原文}`（几句用"；"连接，超过 80 字截断）。判断节点上是折叠掉的那条分支；两条分支都折叠掉、判断变成步骤时记在那个步骤上。只写日志、只有 `pass` 的分支不记。大纲里写成判断下面的一行"是 →（这条分支没有节点，只赋值：…）接着往下" |

带调用的 `return` / `raise` 画成两个节点：先一个步骤（调用），再一个结局（结局节点自己没有 `calls`）。

## 调用（CallRef）与解析等级

| 字段 | 说明 |
|---|---|
| `name` | 显示名，如 `svc.send_mail`；派发是 `派发 任务名`，目标不明时 `派发 未知任务` |
| `target` | 被调用函数的 key（派发时是被派发任务的 key）；没有时为 null |
| `resolution` | `exact` / `guessed` / `unresolved` / `external` |
| `is_dispatch` | 这个调用是派发（`task.kiq(...)`、`DBOS.start_workflow(task, ...)`） |
| `conditional` | 不一定执行：在三元表达式、`and` / `or` 短路里，或在 `match` 的 case 守卫里 |
| `dispatches` | 非派发调用：`target` 内部任意深度会派发的任务 key，排序 |

节点上只收有意义的调用：派发、解析到项目内函数（`exact` / `guessed`）的调用、被 `await` 的调用（任何等级）；构造
对象、日志等噪音不收。所以除了派发，节点上的 `unresolved` / `external` 调用都是被 `await` 的。解析到的和无法判断的
完整清单在函数的 `call_targets` 和 `unresolved` 里。

| 等级 | 含义 | 读图的程序可以依赖什么 |
|---|---|---|
| `exact` | 按静态规则确定的项目内函数：同模块定义、导入、内部函数、`self` / `cls` / 类名上的方法、有类型的参数和模块级实例、别名；调用项目内的类指向它的 `__init__` | 可以直接连线、展开。不考虑运行时替换：子类重写了 `self.m()` 调用的方法时，仍指向本类上的 `m` |
| `guessed` | 接收者类型未知，按方法名推测：调用方所在源码根下这个名字恰好一处定义，而且是类上的方法；派发时是任务名恰好对应一个任务 | `target` 有值但不保证对，要标成"推测"；节点标题不取它的文档注释。它照样进 `call_targets`、参与功能线组装 |
| `unresolved` | 没法判断目标（动态调用、多处同名定义等），`target` 为 null | 调用可能进了项目代码，也可能没有；不要当成"没有调用" |
| `external` | 目标在项目外：标准库、第三方、字面量上的方法（`"".join(...)`）、没有项目内 `__init__` 的类，`target` 为 null | 项目里没有它的图 |

## 连线（Edge）

字段：`src`、`dst`（节点 id）、`kind`、`label`、`branch`、`label_full`。`branch` 只在判断节点的分支出边上有（标明
是哪个分支，见"读连线"第 1 点），只在非空时出现在 JSON 里。`label_full` 只在 `case` 连线的 `label`（模式原文，最长
80 字）被截断时出现，是完整的模式（见"截断与完整形式"）；连线改成 `break` / `loop_back` / `finally` / `raise` 时
和 `label` 一起保留。完全相同的连线只留一条（不看 `label_full`）。连线没有 `sid`，跨两次分析怎样配对见
"两种标识：key 与 sid"一节。

| `kind` | 含义 |
|---|---|
| `next` | 顺序往下：开始 → 第一个节点、语句 → 下一句、捕获节点 → 它的处理体 |
| `yes` / `no` | `if` 判断的两个分支（label 为空） |
| `case` | `match` 判断的一个分支，label 是模式原文（带守卫时 `模式 if 守卫`；最长 80 字，被截断时完整的在 `label_full`）；没有兜底分支时另有一条 label 为 `都不匹配` 的，越过整个 `match` |
| `loop_each` | 循环节点 → 循环体 |
| `loop_back` | 循环体正常走完或 `continue`，回到循环节点 |
| `loop_exit` | 循环节点 → 循环之后（或 `else` 体）：循环正常结束 |
| `break` | `break`：跳到循环之后 |
| `raise` | 异常的落脚点：从 `try` 体的入口节点（某条路径在 `try` 体里没有节点时，从 `try` 之前的节点）连到每个捕获节点；处理体为空（只写日志）的 `except` 吞掉异常后照常往下，连到 `try` 之后；有 `finally` 时也连到 `finally` 体 |
| `finally` | 进入 `finally` 体：`try` / `except` / `else` 里的结局节点，和穿过 `finally` 的 `break` / `continue` |

读连线时要知道的几点：

1. **判断节点的分支 = 它所有不是 `raise` 的出边，每条都带 `branch`，标出是哪个分支；kind 说明控制怎样离开。**
   普通的 `yes` / `no` 连线 label 为空。一条分支离开判断节点后没有别的节点、直接离开所在的块时，这条连线改成
   离开的方式，`branch` 不变，label 也保留（`yes` / `no` 写成 `是` / `否`，`case` 仍是模式）：
   - 分支直接就是 `break` / `continue`：改成 `break` / `loop_back`（要穿过 `finally` 时，进入 `finally` 体的这一段
     改成 `finally`）；
   - 判断是循环体的最后一句、分支走到循环体末尾：改成 `loop_back`，回到循环节点。例如 `for …: if c(): f()` 里判断
     节点到循环节点有一条 label 为 `否` 的 `loop_back`；没有兜底分支的 `match` 在那里有一条 label 为 `都不匹配` 的
     `loop_back`。

   所以一个 `match` 可能一条 kind 为 `case` 的出边都没有。循环头部有调用而循环体为空（或全被折叠）时，循环节点
   没有 `loop_each` 出边，只有一条指向自己的 `loop_back`。循环体一开头就是 `break` / `continue` 时 `loop_each`
   同样改写。判断节点的 `raise` 出边不是分支，是"这条分支上抛出的异常落在哪里"。

   **怎样认出分支（读图的程序照这里做）：看连线的 `branch`。**
   - `if` / `elif` 的分支：`yes` / `no`。没有 `else` 的 `if` 也有 `no`：越过分支体的那一条。`elif` 是嵌套的判断节点，
     各有自己的 `yes` / `no`。
   - `match` 的分支：该 `case` 的模式原文，和这条连线的 label 相同（带守卫时 `模式 if 守卫`；空白合并，过长截断）；
     没有兜底分支时，越过整个 `match` 的那一条是 `else`（label 为 `都不匹配`）。
   - 没有 `branch` 的连线不是分支：判断节点的 `raise` 出边（label 可能写着 `是` / `否`，那是"哪条分支上抛出的"），
     以及别的节点的出边。`for` / `while` 是循环节点，不是判断节点：条件成立 / 不成立是 `loop_each` / `loop_exit`，
     没有 `branch`。
   - 判断节点是 `match` 还是 `if` / `elif`（`match` 的模式也可能恰好写成 `yes`，如 `case yes:`，所以按 `branch` 显示
     "是 / 否"之前先分清节点）：`match` 的判断节点 `subtitle` 以 `match` 加一个空格开头（`match` 加主语原文，如
     `match event.kind`），`if` / `elif` 的 `subtitle` 是条件原文。条件原文自己也可能这样开头（变量叫 `match` 的
     `if match is None:`），要确定时看它任意一条不是 `raise` 的出边：kind 为 `yes` / `no` 或 label 为 `是` / `否` 的是
     `if` / `elif`，否则是 `match`。
   - 读没有 `branch` 的旧图时的回退：kind 为 `yes` / `no` 的是 `if` / `elif` 的分支；改了 kind 之后 label 为 `是` /
     `否`；`match` 的分支看 label（模式原文，`都不匹配` 即 `else`）；kind 为 `raise` 的不是分支。
2. **`raise` 连线可以和同一对节点之间的普通连线并行**：例如 `try` 体以 `if` 开头、`except` 只写日志时，"否"连线
   和异常连线都落到 `try` 之后的节点。同一对节点之间至多一条 `raise` 连线。
3. **跳转穿过 `finally` 画成两段：跳转处 → `finally` 体 → 跳转目标。** 进入 `finally` 体的一段是 `finally`，
   从 `finally` 体出口到目标的一段是 `break` / `loop_back`。跳转处的出边本来就是 `raise` 或 `loop_exit` 的（例如
   内层循环之后紧跟 `break`，出边是内层循环节点的 `loop_exit`），从它出发的那一段保持原类型。套了几层 `finally`
   就逐层经过。跳转处是判断节点的一条分支时，从它出发的那一段（`finally`，或 `finally` 体里没有节点的路径上直接到
   目标的 `break` / `loop_back`）带这条分支的 `branch`；从 `finally` 体出口出发的一段起点是出口节点，照它自己的
   规则（出口是判断节点的分支时带那个分支）。
4. **`finally` 体只画一份**：正常出口、异常、结局、跳转都进同一份，出口照常往后接。所以结局节点在 `try … finally`
   里时有出边（`finally`），图上"结局 → `finally` 体 → 后面的语句"这样的路径不一定真实存在。例外：进 `finally` 体的
   只有结局和没被捕获的异常时（`try` / `except` / `else` 没有正常出口，也没有 `break` / `continue` 穿过），出了
   `finally` 体函数就结束了，它的出口不往后接——`finally` 体的最后一个节点没有出边（自检不算"没有出路"），后面的
   语句是走不到的节点；外层还有 `finally` 时，出口进外层的 `finally` 体（`finally` 连线）。
5. **"未捕获异常退出"节点（`end:uncaught`）没有入边，这是有意的**：任何节点都可能因异常从这里离开函数，连线没有
   信息量。它不算走不到的节点（自检不报）。任务声明了重试时标题是"未捕获异常退出（任务会重试）"。
6. **`match` 判断节点的 `calls` 包括各 case 守卫里的调用**（`conditional` 为 true），它们的位置在节点的
   `[line, end_line]` 之外——这个范围只覆盖 `match` 和主语。按行号把调用对应到节点时要考虑这一点。

## 功能线（FlowLine、LineTask）

| 字段 | 说明 |
|---|---|
| `id`、`sid` | 见上 |
| `title`、`group`、`kind` | 标题（根函数的 `title`；没有标题的接口用 "方法 路径"）；分组（标记的 `group` → 接口所在模块名 / `后台任务` / `其他入口`；挂在路由上的工作流、任务有 `route`，按接口算）；根函数的 `kind` |
| `title_full` | 只在标题取自被截断的函数标题时出现：根函数的 `title_full`（见"截断与完整形式"） |
| `root` | 派发树的根 `LineTask`：`function` 任务函数的 key；`children` 它派发的任务（公共任务除外）；`goto` 为 true 表示这个任务在本条线里已经出现过，不再展开（环也这样断开） |

## 自检（SelfCheck）

| 字段 | 说明 |
|---|---|
| `unreachable` | `[函数 key, 节点 id]`：从开始节点走不到的节点（"未捕获异常退出"不算） |
| `dead_ends` | `[函数 key, 节点 id]`：不是结局、却没有出边的节点 |
| `unresolved_calls` | 各函数 `unresolved` 条数之和 |
| `guessed_calls` | 节点上 `guessed` 调用的个数 |
| `skipped_files` | `[相对路径, 原因]`：解析不了的文件，构建失败的函数（原因里写函数名），以及没有读的 `.py` 路径：指向分析目录之外的符号链接（`符号链接指向项目之外`）、解析后不是普通文件的（FIFO、设备，`不是普通文件`）、项目之内指向非 `.py` 文件的符号链接（`符号链接指向的不是 .py 文件`）——这些从不打开，也不在 `file_hashes` 里。项目之内指向 `.py` 普通文件的符号链接照常按链接的路径分析 |
